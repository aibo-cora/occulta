# v2.0.1 security audit: index (2026-11-10)

Three audits of the v2.0.1 code (`87d9bf11`, `v2.0.1/version-bump`), one per subsystem, each run with the
`occulta-security-audit` skill. This index sits on a `release/v2.1.0` base so the findings are tracked
toward that release. The bugs are in `Docs/Features/Secure Mode/bugs.md`.

Every run is marked **incomplete**, and none of it ran on a device. Production code was not changed.

Numbers 207–209 and 215–219 are unused.

## Highest severity (proposed, unverified unless noted)

- **Bug 220, Critical:** a duress PIN alone reaches the real depth through "Deactivate Protection". Reproduced by a failing test.
- **Bug 227, Critical (conditional):** the grace period is measured on the wall clock, so setting the clock back skips the PIN.
- **Bug 211, Critical on devices upgraded from 1.9.2–1.10.3 with Secure Mode active:** the old layer file stays in the App Group under a key derived from a public point.
- **Bug 198, High:** a man in the middle of the key exchange can make both phones show the same verification words.
- **Bugs 210 and 229, High and Medium:** `secure_delete` is not in effect on SwiftData's connection, so deleted rows stay in the store file.
- **Bugs 221, 222 and 228, High:** depth-dependent observables (a PIN set on a lowered lock, the app-switcher cover, SwiftData's history log).

Secure Mode has seven findings reproduced by failing Simulator tests; the other audits' findings are source-only.
