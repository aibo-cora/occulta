## 1. Negative custodyManifestCount in a group slot traps openGroup
`Contact+Manager/openGroup:negative-custodyManifestCount-prefix-trap`

RecipientPayload.custodyManifestCount is a signed Int taken straight from the slot JSON with no range check. openGroup passes it to Array.prefix when the slot is a forward-secret one-time slot (not long-term fallback, not last-resort, not a card slot) and the sender set shardMetadataAttempted. Collection.prefix(_:) has a non-negativity precondition that stays in optimised builds, and the project sets -Onone only for Debug, so a count below zero terminates the app. The trap comes after the one-time prekey has been consumed and saved and after the inbound batch has been accepted and saved, so the message is lost and cannot be reopened. A contact (or anyone holding that contact's keys) can build such a slot, because the sender chooses every field inside it and holds everything the senderProof and ephemeral-signature gates ask for. Each further bundle traps again. No document in Docs lists this as a known item.

**Claimed root cause.** RecipientPayload's decoder accepts any Int for custodyManifestCount, and openGroup hands it to a precondition-checked standard-library call without clamping it or rejecting a negative value.

## 2. At a duress depth, approving a hidden contact's identity challenge signs a valid response and seals it to that contact
`IdentityChallenge.Coordinator.approvePending/hidden-challenger-reply`

At a duress depth, a fresh identity challenge from contact H, who is hidden there, still decrypts and presents IncomingChallengeSheet ('<H> is verifying your identity'). That much is the presence oracle accepted on 2026-08-13 and in Bug 104, which recorded the name and note render only. The sheet's Approve action is not bound to the depth. approvePending runs an LAContext check (biometrics when enrolled, device passcode only when none is, so a coercer needs the owner's biometric or the passcode, within the compelled-unlock model), looks the challenger up by identifier only, signs the challenge with the owner's long-term identity key, and for a challenger at .bodyDigestCapable seals the response through encryptBundle, which takes one of H's one-time prekeys, saves H's prekey record and attaches any pending batch for H; otherwise it seals the long-term format to H's key. The response .occ is then staged for sharing (ShareActivityView). Once delivered, H's app shows 'Identity verified: <owner> controls their device'. So the coercer replies into a hidden contact, and the reply is the artefact H relies on to check that a request really comes from the owner. The run's threat model names 'reply into' a hidden contact as an action a coercer must not be able to take. The project made the matching decision for cards on 2026-10-19 (SPEC 9: 'nothing leads into a hidden contact') and drops shard operations from a sender not visible at the current depth at receipt (OccultaApp.swift:1000-1026); Bug 40 originally flagged this approval sheet before the gate was removed. No recorded decision covers the outbound action. Gating by visibility would itself be a duress-only difference, so the fix is a design decision (for example a same-size decoy response that verifies for no one and leaves H's record byte-identical, behind the same UI); that choice belongs to the owner.

**Claimed root cause.** IdentityChallenge.Coordinator.approvePending (IdentityChallenge+Coordinator.swift:263-310) and the sealing it calls have no check of the challenger's visibility at Manager.Security.currentDepth: ContactManager.fetchContact(by:) (Contact+Manager.swift:453-459), ContactManager.encryptBundle (Contact+Manager.swift:1055-1196) and IdentityChallenge.Manager.respond (IdentityChallenge+Manager.swift:316-342). ## 3. Outstanding identity challenges and verified-at state survive endSession into a duress session
`IdentityChallenge.Coordinator/session-state-survives-endSession`

The owner, at the real depth, challenges contact H (visible there, hidden at a duress depth) and types a question into the context note. The challenge is recorded in the coordinator's in-memory OutstandingChallengeStore (contact identifier, nonce, timestamp, note). The app later locks past the grace period, or the depth changes in place, and RootView.endSession runs. That is the Bug 140 session boundary, but it clears only the coordinator's three presentations; the store and verifiedAt live on because the coordinator is created once per process (OccultaApp.swift:98) and the store is swept only in Coordinator.init. A coercer then unlocks with the duress PIN. If H's response is opened, by the coercer or drained from the queue, it resolves to H with no depth filter (the accepted presence oracle), matches the owner's real-depth entry by nonce and contact identifier (IdentityChallenge+Manager.swift:391-394), and the coordinator presents 'Identity verified: H controls their device' with 'You asked: <owner's question>'. A response arriving after the one-hour window instead yields 'Verification failed - This may not be H' with the same name and note (:407-410), so the carried entry produces a sheet either way. Without the carried entry the same response returns .notOurs and shows nothing at that depth (Bug 166 fix, Coordinator:247). So what is disclosed is the owner's own hidden-depth text and evidence that the previous session acted on a contact the coercer cannot see, beyond the inbound-name render that Bug 104 accepted; Bug 104's note on .response puts verifiedAt out of scope. The same carried state also shows 'Verification in progress' and 'Verified N minutes ago' on contacts visible at both depths, a weaker signal. Calibration: the trigger needs H's response to arrive or be opened after the handover and while the process is still alive, so it is the same timing-bounded, third-party-dependent class as the accepted passive case, with the additional leak of owner-authored content; it applies to Bug 140's stated invariant (state created at one depth, 'unanswered decisions', must end when the session changes), which the fix list names only for the three presentations. Remediation note: simply emptying the store at endSession would silently break the legitimate flow of challenging, locking the phone for longer than the grace period and then opening the reply (the reply would become .notOurs and show nothing), so the better fix binds each entry, and the verified-at map, to the depth that created it and ignores them at any other depth (a mismatch behaves as 'no entry', a non-observable difference).

**Claimed root cause.** IdentityChallenge.Coordinator is constructed once per process (OccultaApp.swift:98) and owns the OutstandingChallengeStore and verifiedAt. RootView.endSession (OccultaApp.swift:625-639), the single session reset added for Bug 140, clears only outboundShare, incomingChallenge and verificationOutcome (:633-635). The store is swept only at Coordinator.init (IdentityChallenge+Coordinator.swift:94). verifyResponse correlates a response to an entry by nonce and contact identifier alone (IdentityChallenge+Manager.swift:391-394), with no binding to the session or depth that created it.

## 4. Out-of-range SignedAttribute dates in inbound shard operations trap signature verification
`OccultaFormats/SignedAttribute.signingPayload:out-of-range-date-to-UInt64-trap`

SignedAttribute.signingPayload converts createdAt and expiresAt to UInt64 with no range check. SignedAttribute is decoded from the sealed payload by the synthesized Codable with a default JSONDecoder, so a Date can be any Double the sender writes. A contact visible at the current depth can send a forward-secret bundle whose .distribute, .replace or .handback operation carries a createdAt before 1970 (or past 2^64 seconds), or a far-future expiresAt. ShardCustodyManager then calls verify(against:), which builds the signing payload as an argument to SecKeyVerifySignature before any signature is checked, and the app terminates. The surrounding do/catch in handleInbound catches thrown errors only. The same conversion trap was already fixed for .occbak entries (Vault+Manager+Backup.swift isWellFormed, Bug 96 item 1) but not for this inbound path. Because the JSON Date is seconds since 2001, an input such as createdAt = -1e12 or expiresAt = 1e30 is enough.

**Claimed root cause.** The SignedAttribute decoder accepts any Date, and signingPayload, the shared sign/verify routine, performs a trapping Double-to-UInt64 conversion on it. No range validation runs on an inbound attribute before verify().

## 5. Crafted .occ length field traps WireHandle and terminates Occulta before authentication
`OccultaFormats/WireHandle:unchecked-UInt64-length-to-Int-and-offset-add-trap`

WireHandle converts attacker-controlled 64-bit length fields with Int(_:) and adds them to the read offset unchecked. A 167-byte file starting with OCCB and carrying a ciphertext length >= 2^63 (or within 167 of Int.max) makes OccultaBundle.decoded trap instead of throw. The app terminates whenever the file is opened, or at the next PIN unlock if it was queued while locked; the queue is memory-only, so nothing persists across the crash and the effect is a process termination, not memory corruption, and it needs the user to open the file. Anyone who can get a file opened in Occulta can do this: no contact relationship, key or depth is involved. The same pattern in decode(payload:) and decode(basket:) lets a contact, a card holder (before redemption, at every depth), or a group co-recipient of a pre-digest sender trap the receiver after decryption. A trap during a share-extension handoff also skips the deferred removal of group.com.occulta.shared/inbound/<uuid>.occ, which nothing else sweeps (the existing Inbox cleanup covers only Documents/Inbox and tmp). This is a concrete instance of the open 'no fuzzing of .occ decoders' item, not a restatement of it.

**Claimed root cause.** Reader has no checked length helper: callers do Int(UInt64) conversions, and Reader.read computes offset + count before its bounds guard. Swift traps on both in -O builds, and try? at the call site cannot catch a trap.

## 6. Share staging key is a function of the Enclave key's public point, not of its private key
`ShareStagingKeyManager.deriveSymmetricKey:ecdh-with-generator-is-public-point`

ShareStagingKeyManager derives the AES-256-GCM key that seals staged share files and manifests from ECDH(SE private key d, P-256 generator G) using .ecdhKeyExchangeCofactorX963SHA256. For P-256 (cofactor 1) that shared point is d*G, the key's own public point Q, so the ECDH output is X9.63-SHA256 of x(Q), and the HKDF salt is the x9.63 encoding of Q; the info string is a constant. No secret enters the derivation: the AES key is a function of Q alone. The file header and comments present the key as bound to the Secure Enclave. If Q, or a blob from which Q is parsed without an Enclave call, is recoverable from a keychain or filesystem extraction, an examiner holding an image taken while a share session is staged (sessions are swept after 3600 s, and the sweep runs only when the main app is foregrounded) could decrypt the staged files and manifest offline, without calling the Enclave. Impact is bounded: staged files and the manifest are also written with .completeFileProtection, the manifest no longer names a recipient (it lists file names and extensions), and the content is the attachment being shared, not hidden-depth state, so the AES layer only adds protection against an examiner who can read class-A file bytes but cannot use the Enclave. Project docs already treat the Enclave half of this construction as a fixed value that one call during extraction captures (Docs/v2.0.0/HARDENING_STEPS.md:72); this candidate is the stronger observation that the value is computable from public data alone, which no known item records.

**Claimed root cause.** Using the curve generator as the ECDH peer turns the key-agreement step into public-key recomputation (d*G = Q); no secret input enters the derivation, so Enclave binding of the private key does not translate into secrecy of the symmetric key.

## 9. A copy of a group bundle with an altered outer header uses up the recipient's one-time prekey, and the genuine message can then never be opened
`group-outer-header-unauthenticated-before-prekey-consumption`

openRecipientSlot and openCardSlot record the slot's one-time prekey as used once the slot opens and its bodyDigest matches, and a defer then consumes it and SenderPrekeys saves the record at once. The slot AEAD authenticates only `blind`, and the digest covers only bundle.ciphertext. The outer header (secrecy.ephemeralPublicKey, 65 cleartext bytes, and secrecy.prekeyID, a flag plus 36 cleartext bytes) is authenticated only later, as part of the AAD in openGroupCiphertext. A group bundle's header is always the constant mode .group, empty ephemeral key and nil prekeyID, so those fields carry no information, yet the parser accepts any value. Anyone holding a copy of the .occ file can set one byte of the ephemeral field (or the prekeyID flag with 36 valid UTF-8 bytes), keep the sender fingerprint, and deliver the copy first: the slot opens, the digest matches, the prekey is consumed and persisted, and only then does openGroupCiphertext fail. The genuine copy that arrives later finds no key (recipientSlotNotFound). The attacker needs no key; a group member who has the same file at the same time (bugs.md Bug 165 says this is usual) or a holder of a transport copy qualifies. The project fixed the same outcome for a rewritten body (the Bug 165 amendment to SECURITY_CHECKLIST.md section 2.2) and stated the rule: delivering first must not make the genuine message unopenable. The 'prekey burn' cost accepted at SECURITY_CHECKLIST.md:91 is framed around someone holding the batch we published, who can burn keys with bundles that open and fail; it does not discuss a keyless copy-holder destroying one specific genuine message, so this is treated as an uncovered variant of that item and the Bug 165 exception, not a restatement. Scope: one message per tampered copy; availability only; the single-recipient path (decryptSealed) is not affected because it opens under the full AAD before consuming. Suggested fix: refuse, before trial decryption, a group bundle whose outer secrecy is not the constant every sender writes, or open the outer ciphertext before the prekey is recorded as used.

**Claimed root cause.** The one-time prekey is recorded as used, and so consumed and persisted, when the slot AEAD (AAD = blind) and the ciphertext digest pass. Neither covers the outer SecrecyContext. The AEAD that does cover it (openGroupCiphertext, AAD = version, sorted-JSON secrecy, blind) runs only after consumption, and the wire parser does not require the constant header values a group bundle always has. The Bug 165 digest reasoning ('changing either changes the ciphertext') holds only for someone who re-encrypts, not for an AAD-only change by a keyless holder.

## 11. A coercer at a duress depth can re-open archived re-openable .occ files from a hidden contact and read them on demand
`occulta/inbound/duress-reopen-of-archived-reopenable-bundle-from-hidden-contact`

The inbound path resolves the sender over contacts at every depth (identifyOwner reads fetchAllContacts, which filters only deletionToken) and nothing on the way checks Contact.isVisible against the current depth, so a bundle from a contact hidden at a duress depth opens and the read sheet shows the message with that contact's name, phone and email. That is the presence oracle accepted on 2026-08-13 (Bugs 103/104). Its written rationale limits the content exposure to a new message from a real third party arriving during the coercion window, 'timing-bounded and not adversary-controlled', and says content confidentiality is a separable question that was not taken up. Bundles sealed on a re-openable slot are not single-use: a long-term fallback slot derives its wrapping key from the two long-term keys and consumes nothing, and a last-resort slot keeps its key until it retires (Bug 82 table; Prekey Continuity D5, decided 2026-10-07 as 'messages may reopen'). Fallback carries the first message of a relationship in each direction and about 1 in 16 after it, plus last-resort sends. A coercer holding the unlocked phone can open any retained copy of such a file from the transport (Messages, Mail, Files; .occ is a registered document type) through Open in Occulta and read content written long before the coercion, repeatedly and on demand. That is adversary-controlled and not bounded by the window, so the acceptance rationale does not obviously cover it. Each successful open also saves the hidden contact's prekey record, and a replayed long-term bundle with no batch pending makes replenish install a fresh prekey batch into that record. Calibration: the re-openability itself is a known, documented cost (Bug 82a, D5, and the compose indicator copy 'Multiple Views - Long-Term Key ... Hold back anything sensitive'), and the exposure is limited to messages that were sealed on those slots and are still retained, not to all history. The new element is the in-app route at a duress depth, which the existing decisions do not address. The codebase does gate one stateful action for hidden senders at receipt (filterShardOperations drops shard operations from a sender not visible at the current depth), so the absence of a gate on message content here is a decision, not an oversight; whether it extends to replay is the owner's call.

**Claimed root cause.** Two properties combine: the inbound path resolves and decrypts for contacts at every depth by design (identifyOwner over fetchAllContacts, no visibility check), and bundles on long-term fallback and last-resort slots are not single-open, so any retained copy decrypts again. The presence-oracle acceptance assumed only newly arriving messages reach that path; nothing makes an already-opened re-openable bundle fail the way a consumed forward-secret bundle does, at every depth.

## 13. Card conversation on a revoked contact seals replies to the revoked device's prekeys

## 18. After a contact's clock goes back, a replayed bundle on a reopenable slot can bring back their newest-dated batch, whose keys they have already deleted
`prekey-accept-reopenable-slot-replay-of-newest-dated-batch`

PrekeyBookkeeper.accept blocks batch replays with a window of the last 8 accepted batch IDs and, on slots that open again (long-term or last-resort), a date rule that refuses only a batch strictly older than the newest date ever accepted (`generatedAt < newest`). On one-time slots a new ID alone is enough, by design (Bug 158), and the stored maximum is never lowered. If the contact's clock goes back, the batch with the highest date (B_hi) sets the maximum, and eight later batches dated earlier are accepted on our one-time keys by ID alone. They push B_hi's ID out of the window without raising the maximum. A holder of an earlier file in which that contact sent B_hi on a long-term or last-resort slot can then deliver it again: the slot reopens, B_hi's ID is unknown, and `generatedAt == newest` passes the strict comparison. B_hi's one-time keys are appended (possibly evicting the oldest held batch, the cap is 2) and its last-resort key replaces the current one. The contact has used up and deleted those keys, so messages we later seal to them cannot be opened: up to 15 one-time sends and the last-resort slot are lost. The replay can be repeated after eight more batches. The code comment at PrekeyBookkeeper.swift:142 and DESIGN.md:361 state the intent that a replay is older than whatever was accepted since; that fails exactly at equality. The open item at DESIGN.md:369 (Bug 158, clock went back) covers refusal of the contact's new batches, not acceptance of a replay, so this is recorded as a new variant. Likelihood is low: it needs a clock-back sender, at least eight of their batches accepted on one-time slots while the clock stays behind B_hi's date (roughly 80 or more messages from us), and a kept copy of a bundle that carried B_hi on a reopenable slot. The only effect is lost availability of our messages to that one contact, bounded and self-correcting once the stale keys are used. Suggested fix: refuse `generatedAt <= newest` at PrekeyBookkeeper.swift:134; any genuine new batch is dated strictly later.

**Claimed root cause.** The date gate at PrekeyBookkeeper.swift:134 compares strictly (`generatedAt < newest`) against latestInboundGeneratedAt, the maximum date ever accepted. The ID window (lines 135-138) can drop the ID of the batch that set that maximum without the maximum moving, so a replay of that batch passes both checks.
