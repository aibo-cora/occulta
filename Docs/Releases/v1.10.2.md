# Occulta 1.10.2 — Release Note

**Marketing version:** 1.10.2 · **Build:** 2 · **Branch:** `release/v1.10.2`

---

## App Store — What's New

> **Stronger sender verification.** Messages now carry a signature proving who sent them, checked
> against a key that never leaves your device's Secure Enclave. Occulta verifies it on every
> message it opens.
>
> **Some contacts may need to update.** Versions before 1.10.0 don't add this signature. If a
> message won't open and Occulta suggests asking the sender to update, that's why — once they're
> on the latest version, their messages open normally.
>
> **Vault recovery shares reach more contacts.** Contacts running recent versions were being left
> out of recovery-share distribution without any sign of it. They are included again.
>
> **Also fixed:** an issue that could leave previously created groups unreadable — affected groups
> are cleared when you update and can be recreated — and a problem where contacts could be
> incorrectly shown as needing an app update.

---

## Why it is worded that way

**It never links the symptom to Secure Mode, and that is the real constraint** — sharper than
"don't name the feature". Secure Mode is already visible to anyone holding the phone; its
existence is not the secret. But a note saying *"messages may fail if you've used Secure Mode"*
would hand a coercer a decoder ring: observe a message fail, conclude the user activated it. The
public note would become the oracle this release exists to close. The rejection is framed purely
as version compatibility, which is also literally true.

**The group fix is stated plainly.** Group loss is visible at every depth and reveals nothing
about duress state, so there is no mapping to avoid.

**It says affected groups are cleared.** Users will watch groups disappear on update; better they
read why than file a bug.

**It does not describe the vulnerability.** "Stronger sender verification" does not advertise that
enforcement was silently off in 1.10.0 and 1.10.1. Standard practice — detailed disclosure before
users have updated helps attackers more than users.

**The recovery-share line is new since the first draft.** A capability comparison used `==` where
it needed `isAtLeast`, so every contact on 1.10.0 or newer failed the check and was silently
dropped from shard distribution, custody manifests, and expected-share lists. The padding pass ran
regardless, so bundles kept their normal shape and nothing surfaced. It is worth a line because
users may have wondered why a trustee never appeared to receive anything.

## Not in the user-facing note, and why

| Change | Why it stays out |
|---|---|
| Domain-separated `senderEphemeralSignature` behind a 1.10.2 capability tier | Wire-format detail with no observable behaviour for anyone on a current build |
| Prekey now consumed the moment a slot opens, not after the message is judged | Internal; the observable effect is that forward secrecy is delivered where it previously was not |
| Design documents removed from the shipped app bundle | Not user-facing. Saves ~350 KB, but saying so invites the question of what was in them |
| Orphaned-group sweep moved behind an authenticated depth | Describing when it runs would describe the depth model |
| Temp-file and share-manifest protection classes | Hardening with no observable behaviour |
| `consume()`'s status no longer discarded | Diagnostic only in release builds |

## Accepted limitations shipping with this release

Each is documented in full at the reference given; this is the summary a support conversation
would need.

- **Bug 81 — contacts on 1.9.x may be unable to reach you.** If your record of their version was
  stranded by an earlier key rotation, their forward-secret group messages are rejected until they
  reach 1.10.0. There is no action available to either side before then; the marker cannot heal
  below that version by design, because letting it would reopen what this release closes. This is
  what the "ask this contact to update" message covers.
- **Bug 82 — a contact re-exchanging keys loses messages already in flight.** Anything sealed
  before the re-exchange fails to open, permanently. Narrow window, availability only, deferred on
  likelihood.
- **Bug 83 — a contact who downgrades below 1.10.2 stops receiving your forward-secret group
  messages.** Intermittent rather than flat: roughly fifteen lost, then one that lands, repeating.
  Requires TestFlight or a restore onto an older build, since the App Store offers no downgrade
  path. **If a user reports flaky delivery to one specific contact, check that contact's version
  first.**
- **swift-crypto ships unused.** An SPM dependency that nothing calls, carrying vendored BoringSSL
  in five resource bundles. The crypto actually in use is Apple-framework-only. Removing it is
  queued for the next tag.

References: `Docs/Features/Secure Mode/bugs.md` (Bugs 77–83),
`Docs/Audit/SECURITY_CHECKLIST.md`, `Docs/Audit/SecurityReview2026-08-12/README.md`.
